StT-WhisperAI · Web Portal

Portal web multi-user berbasis Docker. Setiap user terdaftar bisa upload rekaman, mengelola file, dan mengirim job transkripsi ke antrian tunggal yang dikerjakan satu per satu oleh worker GPU. Admin mengelola user, kuota, dan antrian.

Arsitektur

Empat container. Web dan worker memakai kode yang sama (app/), tapi hanya worker yang memuat model AI dan memakai GPU. Postgres menjadi sumber kebenaran untuk user, metadata file, dan antrian job. Isi file disimpan di FRI Mini CDN (layanan eksternal); portal hanya menyimpan cdn_file_id.

Kepemilikan file ada di portal. CDN hanya mengenal satu aplikasi (satu API key untuk seluruh portal), jadi pemisahan file per user, folder, nama tampilan, dan rename dikelola di tabel files Postgres. CDN tidak punya fitur rename/folder.

Hasil transkripsi (teks + segmen + speaker) disimpan di Postgres. Format txt/srt/vtt/json dibuat saat diunduh, jadi tidak tergantung tipe file yang diizinkan CDN. Salinan .txt juga diarsipkan ke CDN.

Kendala: saat diuji, CDN hanya menerima image/jpeg, image/png, image/webp, application/pdf, text/plain, application/zip. File audio ditolak (422).

Solusi yang diterapkan: portal mengecek (cache 1 jam) apakah CDN menerima audio dengan meng-upload file uji kecil lalu menghapusnya. Jika belum, audio disimpan lokal; worker memindahkan file lokal ke CDN tiap jam saat idle, dan admin bisa memicu lewat tombol Cek CDN & sinkron.

Kenapa antrian di Postgres, bukan Redis/Celery? KEPUTUSAN

  • Satu GPU = satu job — throughput tidak butuh broker terpisah.
  • Posisi antrian & fairness mudah dihitung dengan query SQL biasa.
  • Cancel, retry, prioritas cukup update kolom; semua tercatat di satu tempat.
  • Container lebih sedikit, backup cukup satu database.

Alternatif jika nanti butuh banyak worker/GPU: Redis + RQ/Celery. Interface worker dibuat terpisah supaya mudah diganti.

Hubungan dengan app desktop TETAP ADA

  • run.bat + GUI tkinter tetap jalan seperti sekarang.
  • Logika inti (app/processor.py, app/speaker.py) dipakai bersama oleh desktop dan worker.
  • Kode portal di app/portal/, tidak mengubah alur desktop.

Antrian Job (Batch Queue)

Semua permintaan parsing dari semua user masuk ke satu antrian. Worker mengambil satu job setiap kali, sehingga GPU tidak pernah menjalankan banyak job bersamaan.

Siklus status job

queued→ running→ done atau failed / canceled

Saat running, worker menulis progress (0–100) dan stage (mis. "Transkripsi 12:30 / 58:00", "Speaker: diarization 40%") ke tabel jobs. Halaman user membaca nilai ini tiap 3 detik.

Aturan antrian

  • Concurrency: 1 job per worker. Tambah kapasitas = tambah replika worker (GPU lain).
  • Fair share: job berikutnya diambil dari user yang paling lama tidak dilayani, baru urutan waktu submit. Satu user tidak bisa memonopoli antrian.
  • Batas per user: maks. MAX_QUEUED_PER_USER job menunggu (default 3).
  • Prioritas: admin bisa menaikkan prioritas job tertentu.

Ketahanan

  • Heartbeat worker tiap 10 detik ke DB.
  • Job running tanpa heartbeat > 2 menit dianggap macet → kembali ke queued (maks. 3 percobaan).
  • Timeout per job (JOB_TIMEOUT_MIN).
  • Model tetap dimuat di worker antar job → tidak ada waktu load ulang.

Yang dilihat user

  • Job miliknya: status, progress bar, stage, posisi antrian, perkiraan mulai.
  • Ringkasan antrian global: "1 berjalan · 4 menunggu" (tanpa nama file/user lain).
  • Tombol Cancel untuk job miliknya yang masih queued/running.
  • Notifikasi di portal saat job selesai/gagal.

Lihat hasil

Contoh tampilan halaman "Job Saya".

-- Worker mengambil job berikutnya (fair share + prioritas), aman untuk banyak worker
SELECT j.id FROM jobs j
JOIN users u ON u.id = j.user_id
WHERE j.status = 'queued'
ORDER BY j.priority DESC, u.last_served_at ASC NULLS FIRST, j.created_at ASC
LIMIT 1
FOR UPDATE OF j SKIP LOCKED;

Keamanan

Akses

  • Password argon2, rate limit login
  • Session cookie httpOnly + SameSite, CSRF di semua form
  • Setiap query file/job difilter user_id (user tidak bisa akses milik orang lain)

File

  • File terenkripsi di CDN; tidak ada URL publik permanen
  • Validasi ekstensi + cek audio via ffprobe sebelum upload
  • Download lewat endpoint portal yang cek kepemilikan; kunci CDN tidak pernah dikirim ke browser

Operasional

  • Hanya Caddy yang membuka port; db & worker di network internal
  • Audit log aksi penting
  • Backup harian pg_dump (file sudah tersimpan di CDN)

Roadmap Pembuatan

Fase 1 — Fondasi 1–2 hari

  • docker-compose (web, db, caddy), model DB (create_all)
  • Login/logout, seed admin dari .env, wajib ganti password

Fase 2 — File Management via CDN 2 hari

  • Client CDN (token cache, retry, rate limit), upload dengan progress, folder, rename/hapus/download, kuota

Fase 3 — Antrian & Worker GPU 2–3 hari

  • Tabel jobs, claim SKIP LOCKED, fair share, heartbeat, retry, timeout, cancel
  • Worker container GPU memakai processor.py + speaker.py

Fase 4 — Halaman Job & Hasil 2 hari

  • Job Saya (progress live, posisi antrian), viewer hasil + audio player, mapping nama speaker, download

Fase 5 — Admin Portal 2 hari

  • Kelola user, semua job, pause antrian, status sistem, audit log

Fase 6 — Hardening 1–2 hari

  • Rate limit, retensi file, backup, uji beban (beberapa user submit bersamaan)

DITAHAN — Generate MoM dengan LLM setelah portal stabil

  • LLM di server terpisah; portal memanggil API-nya sebagai job tipe mom di antrian yang sama

Catatan & Perlu Diputuskan

CDN belum menerima file audioDiputuskan: minta admin CDN menambahkan MIME audio (audio/mpeg, audio/mp4, audio/x-m4a, audio/wav, audio/flac, audio/ogg, audio/webm, video/mp4) dan cek batas ukuran upload. Sementara itu audio disimpan lokal dan otomatis pindah ke CDN setelah diizinkan.
Deploy di server LinuxDiputuskan: stack dijalankan di server Linux terpisah dengan Docker Engine + NVIDIA Container Toolkit. Langkah deploy ada di README.
Satu GPU dipakai bergantianKalau GUI desktop dan worker Docker jalan bersamaan di PC yang sama, keduanya rebutan VRAM. Disarankan: server portal di mesin terpisah, atau desktop dipakai hanya saat worker di-pause.
Pendaftaran userOpsi A: hanya admin yang membuat akun (disarankan untuk internal). Opsi B: user daftar sendiri lalu menunggu persetujuan admin.
AksesHanya jaringan kantor (PUBLIC_HOST=:80), atau perlu diakses dari internet (isi domain di PUBLIC_HOST → HTTPS otomatis, lalu COOKIE_SECURE=1)?
Jumlah user & volume rapatPerkiraan user aktif dan jam rekaman per hari menentukan apakah 1 GPU cukup (±1 jam audio ≈ 3–6 menit di RTX 3050 tanpa speaker; lebih lama dengan speaker).
Retensi & privasiBerapa lama file audio dan hasil disimpan? Apakah admin boleh melihat isi transkrip user, atau hanya metadata job?
